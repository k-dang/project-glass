# OpenCode implementation verification

Updated 2026-11-12, America/Toronto. The implementation adds ordinary OpenCode Agents and a fresh
Docker Cloud provider. Tours, Agent reviews, review Follow-ups, and the Global conversation retain
their existing programs.

The tested pairing is OpenCode **1.19.5**, `@opencode-ai/sdk` **1.15.13** through `/v2/client`, and
Docker Sandboxes CLI **0.50.1**. `/v2/client` names the legacy SDK export, not OpenCode 2 support.
The Docker template supplies OpenCode; the Plugin installs a private Node 24 runtime for Glass.

### Bounded simplification

The existing runtime module now owns process startup, readiness, event connection, and recovery.
The adapter keeps one active-Turn record containing its first prompt, deliveries, and Stop flag,
instead of separate pending-message, admission, and prompt-root collections. Each delivery owns
its admission, completion, and consumption facts. The Turn mapper receives delivery status in its
reconciliation snapshot rather than tracking completion a second time.

Related cases are combined into **12 recorded workflows**, retaining the regression assertions
from the former 20 scenarios. Eight superseded recordings were deleted. All 12 workflows passed
against real OpenCode 1.19.5; their replay and the two focused Turn tests passed. No new modules,
features, cloud resources, or review round were added.

Final validation after simplification passed **802 workspace tests** (2 skipped): 350 desktop and
452 server tests, using `pnpm -r test --maxWorkers=2`. The 3 Docker provider tests, formatting,
lint, types, and build also passed.

On 2026-11-13 the twelve OpenCode recordings were converted losslessly to NDJSON: one
program/version header followed by one compact frame per line. All 4,583 frames retain the same
values and order. The reader validates each line with the existing schemas, and the recorder writes
the same format. Formatting excludes these generated logs so it cannot expand them again. The
pagination scenario and every regression assertion are unchanged; no native re-recording was needed.

OpenCode tests reuse the existing AgentAdapter/session harness. Their HTTP/SSE fixtures come from
the real pinned OpenCode program against the existing local model fixture, with isolated native
configuration, data, state, cache, and a disposable git repository. Replay needs neither the
program nor a model login. Provider-error responses are generated by that model fixture, then
recorded after OpenCode handles them.

Replay now runs the actual startup code with a recorded process boundary. It matches launch
arguments, working folder, native configuration (including selected skills), authenticated HTTP
requests, and health/version handling. Random ports and credentials are normalized; secrets are
not recorded. Native process crashes are real in recording mode. Tests for lost abort responses
and unavailable event subscriptions inject failures at the HTTP boundary and record those failures.
Replay delivers HTTP data asynchronously. A complete final block of unissued history/status/request
reads may be omitted when HTTP completion and SSE idle coalesce; mutations, semantic events, cursor
values, and all requests actually issued still match. This does not permit dropping partial read
blocks or accepting an unmatched outgoing request.

The scenarios cover:

- Streaming reasoning, tools, and text; changing model and effort; restoring defaults after a
  native process restart; continuing the same native conversation.
- Allowing and denying Permissions, and answering a structured Question.
- Steering an active tool, stopping it, returning an unconsumed Steer, and sending a fresh Turn.
- Images, resolved Mention/Feedback context, native Commands, and selected skills.
- Reconciling a Turn that finishes across a lost native event connection.
- Stopping a waiting request and refusing to replace a deleted native conversation.
- Concurrent Agents and command discovery, with separate conversations.
- A rejected model request followed immediately by a successful fresh Turn.
- Permissions and Questions from descendant sessions, including bypass behavior for child asks.
- Stopping immediately after send, stopping a Command before completion, and recovering when an
  abort response is lost.
- Missing default models before an assistant exists, and rejecting model/effort settings without
  changing the last successful configuration.
- Repeated stream loss, native crashes during a tool, and recovery that exhausts its retries.
- Native auto-compaction and its continuation, including compaction at the start of a Turn after
  switching to a smaller model, and a subtask Command's synthetic continuation prompt.
- More than 100 messages in one Turn, recorded with 105 read-tool steps and native snapshots
  disabled to keep recording fast. Responses preserve OpenCode's opaque page cursor headers.
- A new message submitted immediately after a crash, before restart completes, followed by a
  third distinct message to detect misattributed replies.
- An unconsumed Steer returned when the abort request itself is dropped, then removed from native
  history before a fresh message, even when cleanup initially finds the native process unreachable.

Two focused Turn-machine tests check late output from an earlier Turn and unchanged history
reconciliation. Selected skills use their own Command name, separate from the configuration
Command, so one cannot shadow the other. Fresh replies and undelivered Steers use distinct
markers, and the native recording asserts that returned Steers do not leak into the next prompt.

## Independent review corrections

Claude Opus 5.5 reproduced failures that the initial happy-path checks missed. The adapter now
routes requests by native session ancestry, answers child Permission asks in bypass mode, and
keeps Questions interactive. Sending a prompt or Command returns control to Glass while its owned
native HTTP request runs in the background. Stop fences admission and completion, aborts late
starts, and serializes against steering. A failure before an assistant exists is reported by the
owned request, without exposing the uncorrelated native error event's stack trace.

Configuration commits only after validation and the native update succeed. Recovery retains the
interrupted Turn's identity and makes new sends wait for the replacement connection. Successful
connections reset retry accounting. Reconciliation pages back only to the current prompt, skips
unchanged parts, and ignores the duplicate legacy idle signal. A repository-independent local
model picker says **Default model** rather than claiming the home folder's default also applies
to a worktree or saved conversation. Docker removal also accepts its explicit deleted state.

The original live Glass checks below predate these corrections. The new failure-path checks use
the same real OpenCode 1.19.5 locally with isolated configuration; no additional cloud machines
were provisioned for the review corrections.

The second review corrected the run boundary as well as individual error cases. Native synthetic
user messages after the Glass prompt belong to the same Turn. Ending waits for the owned HTTP
requests to finish as well as native idle, so compaction cannot end a Turn early. Every pending
delivery retains its Turn and actual process identity, rechecks ownership after reconnection and
before sending, and stamps its Prompt/Delivered inputs with the Turn ID. Restart fails work sent
to the dead process without failing unsent work waiting for its replacement.

History uses the native `X-Next-Cursor` value, rather than assuming that a message ID is a cursor.
Reconciliation runs serially and the Turn loop waits for it, preventing overlapping reads from
being cancelled while another read ends the Turn. Cleanup treats an SDK result with no HTTP
response as an expected failure, preserving the discard list for retry instead of throwing a
defect. The per-Turn event-ID set has one owner and is updated in place; deduplication no longer
copies its accumulated contents for every event. The reviewer's streamed-event benchmark was
rerun against the actual machine after the correction, without adding timing assertions to tests.

Two real-program behaviors affected the implementation. OpenCode's first-run database migrations
race when servers start together, so startup is serialized. Its error handler announces idle
before failed-message cleanup persists completion, so Glass waits for the assistant message to
settle before ending the Turn. Each process uses an OS-selected private port rather than
OpenCode's preference for 4096 when given port zero.

The Docker provider tests also check that discovery starts no process, the copied Plugin contract
matches Glass, targets are inspected afresh, a stopped machine is distinguished from a gone one,
and cancellation waits for an accepted create before deleting the recorded machine.


## Glass and Docker

The [verify-glass skill](../../.agents/skills/verify-glass/SKILL.md) drove isolated Electron instances
through the real renderer, backend, RPC, Plugin, and Docker CLI. No user Plugin directory or user
Glass database was modified. GitHub access for `docker/welcome-to-docker` was read-only; no branch
or file was pushed.

Run `opencode-cloud-acceptance` proved creation, messaging, Changes, and reconnection:

1. New Agent offered **Docker Cloud Sandboxes → OpenCode → Big Pickle** without a local OpenCode
   installation. The model picker allocated no machine.
2. Agent `agent/keen-heron-9927c198` used a 1 CPU / 2 GiB native OpenCode machine, with 24-hour
   expiry and automatic deletion. Only Glass host port 7310 was published.
3. The Agent ran bash, wrote `glass-proof.txt`, and replied `GLASS_OK`. Changes showed
   `GLASS_TOOL_OK` against `main`.
4. A filesystem-gated tool was observed running. The entire Electron app and backend were closed.
   The remote Glass host remained alive; releasing the gate while Glass was closed completed the
   tool. Reopening Glass recovered one copy of `REMOTE_RECONNECTED_OK` in the same Agent.
5. A follow-up without tools correctly recalled the original `GLASS_OK` confirmation.

This machine stayed running across the overnight pause, as the configured 24-hour policy permits.
A local DNS outage interrupted Docker credential refresh during that pause; Retry recovered the
Agent once connectivity returned. Its removal confirmation was initially left pending when the
verification instance was closed, so its exact machine ID was then deleted with the Docker CLI.

A separate run, `opencode-cloud-removal`, proved the entire create/message/remove path through
Glass, including the discard confirmation. Agent `agent/clever-lynx-c2e8001c` wrote
`remove-proof.txt`, replied `REMOVE_READY`, and was removed using **Remove Agent**. The UI returned
to an empty Agent list; inspecting its exact Docker ID returned **not found** before the
verification instance was stopped.
