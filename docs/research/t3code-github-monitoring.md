# T3 Code GitHub monitoring research

Inspected 2026-11-01 at commit [`5732bbee397f0a2b0e61d0c2e432f01dca6df3dc`](https://github.com/pingdotgg/t3code/commit/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc), committed 2026-11-01T02:50:57Z. Source review only; no runtime verification. Recommendations below are judgments for Glass, distinguished from observed T3 behavior.

## Main recommendation

Borrow T3's shared GitHub request policy first: bounded concurrency, account-scoped rate-limit pauses, and a quota reserve for interactive actions. Then make the existing Glass polling share in-flight reads and refresh expensive information only when its own signals change. Glass already has useful batching, incremental reconciliation and visibility-aware polling, so adopting T3's whole orchestration/watch framework would add unnecessary complexity.

## Watch correctness worth remembering

One policy choice should not be copied blindly: interactive requests set `allowPaused: true`, bypassing the shared pause as well as being allowed to spend the quota reserve (the quota floor of one still applies). See [interactive policy admission](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/packages/source-control-github/src/server/GitHubRequestPolicy.ts#L394-L410) and [pause check](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/packages/source-control-core/src/server/SourceControlRateLimit.ts#L103-L120). For Glass, reserve headroom for interactive work but honor an explicit GitHub cooldown across both traffic classes, following [GitHub's guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately).

T3 preserves notification baselines per head: new commits reset check notifications; failures can wake immediately while other checks still run; required-check completion is distinguished from advisory jobs. It ignores its own comments and counts comment-only wakes toward a ten-update loop limit. Remarks use a timestamp plus IDs at that timestamp, avoiding missing late comments with the same timestamp. An incomplete comment read never advances the watermark. [Pure watch evaluation](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/orchestration-v2/pullRequestWatch.ts#L10-L155), [pagination completeness](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/orchestration-v2/PullRequestWatchReactor.ts#L309-L383).

Rate-limited watch reads do not count toward the eight-consecutive-read-failure stop limit. End-of-watch logging records duration, quiet duration, read count, wake count and reason. These concepts become relevant if Glass adds explicit agent babysitting; they are unnecessary machinery for ordinary PR-list refresh. [Failure handling](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/orchestration-v2/PullRequestWatchReactor.ts#L486-L500), [lifecycle log](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/orchestration-v2/PullRequestWatchReactor.ts#L235-L255).

## What to adapt to Glass

1. **Shared quota and backoff policy — highest priority.** Distinguish tagged rate-limit errors from generic unavailability, retain retryAt, and pause background reads across the mirror, Queue and open-workspace monitoring under the same credential. Keep interactive reads and writes useful through a reserve. Choose concurrency from measurements rather than copying eight.
2. **Share reads, not just serialize them.** Concurrent requests for the same connection/repository/PR should await one in-flight result. Keep a pending-refresh marker so a mutation or explicit refresh during a read cannot get lost. T3's project grouping and worker demonstrate both requirements without requiring Glass to adopt its entire orchestration model.
3. **Cheap metadata signals and explicit observation time.** Refresh check/review status independently of discussions or diffs. Preserve the pinned Revision and signal that GitHub changed rather than replacing the user's workspace. Polling intervals can depend on pending checks and actual attention. Do not rely solely on updatedAt: T3's own fingerprints include separate check-state counts and still have periodic catch-up.
4. **Conditional REST reads where repeatedly polling REST.** Useful for unchanged check/status endpoints. Glass already batches GraphQL, so measure cost and payloads before adding a second fetching path or copying T3's multi-endpoint revalidator.
5. **Freshness visibility — our addition, not an established T3 advantage.** Expose last successful check observation and a refresh problem when a retained badge is stale. T3 retains recent good summary/detail data after transient/rate-limit failures and logs a warning; the reviewed fallback does not itself attach stale/error metadata to returned values. Its watches explicitly use strict detail reads. [Fallback](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/pullRequest/PullRequestService.ts#L2733-L2780), [strict watch read](https://github.com/pingdotgg/t3code/blob/5732bbee397f0a2b0e61d0c2e432f01dca6df3dc/apps/server/src/orchestration-v2/PullRequestWatchReactor.ts#L474-L484).
6. **Targeted tests.** Exercise shared-pause behavior, an explicit refresh arriving during a held read, shared readers issuing one request, head changes invalidating old checks, and incomplete conversation pages preserving the watermark. These test current correctness properties rather than timer counts.

Avoid copying T3's cross-provider registry, event-sourced orchestration, persistent multi-scope cache, full watch lifecycle, or exact numeric intervals without a present Glass requirement. Its feature surface is substantially broader than Glass's current monitoring needs.
